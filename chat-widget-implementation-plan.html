1Key decisions to review

Everything else follows from these calls. Marked DECIDED (established earlier), REVIEW (yours to make), or NEW IN V2.

D1 — Transport to the browser: SSE over a POST fetch stream DECIDED Unchanged from v1. The gateway abstraction is entirely server-side; the browser always speaks the same NDJSON protocol to /api/chat regardless of which provider served the answer. Provider switching is invisible to the client.
D2 — Model routing via aliases, not hardcoded ids NEW IN V2 REVIEW Application code never names a concrete model. It requests a role alias — "chat" (main assistant) or "cheap" (phase-2 utility calls like suggestion generation). Aliases resolve through lib/llm/config.ts, overridable per environment: LLM_CHAT_MODEL=anthropic:claude-haiku-4-5 → switch to groq:llama-3.3-70b or openai:gpt-4o-mini by changing one env var, zero deploys of code. Review: proposed defaults — chat = anthropic:claude-haiku-4-5, cheap = groq:llama-3.1-8b-instant. Agree?
D3 — Grounding: curated context stuffing, no RAG REVIEW Unchanged from v1: system prompt from config/*.ts + blog frontmatter only (~8–15k tokens). Note the multi-provider consequence: context must fit the smallest context window in your provider pool (Groq-hosted open models can be 8–32k). The curated approach keeps every provider viable; full-corpus stuffing (~50k tokens) would silently rule some out. Review: still fine?
D4 — Persistence: localStorage only, no database DECIDED Unchanged from v1.
D5 — Rate limiting: Upstash Redis, fixed per-IP budget REVIEW Unchanged from v1 (10 msgs / 5 min, 40 / day per IP, hard input/output caps). Now enforced before the gateway is invoked, so limits are provider-independent and one budget covers all keys. Review: envelope numbers.
D6 — Adapter strategy: internal gateway interface, adapters backed by the Vercel AI SDK NEW IN V2 REVIEW Honest reversal from v1: with one provider, hand-rolling the Anthropic stream was the simple option. With four+, hand-rolling means reimplementing streaming, error taxonomy, and (phase 2) tool-calling semantics per provider — that's the AI SDK's whole job, and its @ai-sdk/* provider packages are maintained adapters for exactly your list.

Proposed shape: we still define our own narrow interface (LLMProvider, §3) and our own folder-per-provider structure (§5A). Each provider module is a thin (~30-line) adapter that maps our interface onto @ai-sdk/anthropic, @ai-sdk/openai, @ai-sdk/google, @ai-sdk/groq. App code imports only our interface — if we ever drop the AI SDK, we rewrite adapters, not the app.

Review — alternative B: adapters on native SDKs (@anthropic-ai/sdk, openai, …). Maximum control, no AI SDK dependency, but ~4× the adapter code and we own tool-calling normalization across providers in phase 2. I recommend A.
D7 — Rich actions ship in phase 2 DECIDED Unchanged from v1. Note: phase-2 tool use goes through the gateway's normalized tool interface, so agent behaviors work identically on any provider that supports tool calling (all four do).
D8 — Failover: automatic fallback chain, off by default NEW IN V2 REVIEW The gateway supports an ordered fallback list (LLM_CHAT_FALLBACKS=groq:llama-3.3-70b,openai:gpt-4o-mini): if the primary returns 429/5xx before the first token, retry the next provider once. Never mid-stream (a half-answer from model A finished by model B reads as nonsense). Recommend shipping the mechanism but leaving the env var unset initially — a portfolio can tolerate a rare "try again" bubble, and silent failover hides provider problems you'd want to notice. Review: enable from day one, or keep dark until needed?

3New / updated type interfaces

Gateway contract — lib/llm/types.ts NEW IN V2

The heart of the provider-agnostic design. App code (the chat route, future features) imports only these types — never a provider SDK.

// ── Provider identity ───────────────────────────────────────────
type ProviderId = "anthropic" | "openai" | "google" | "groq";
// extending = add a literal here + one adapter file + one env key (§5A)

type ModelRef = `${ProviderId}:${string}`;      // "anthropic:claude-haiku-4-5"
type ModelAlias = "chat" | "cheap";             // what app code asks for

// ── Provider-agnostic request ───────────────────────────────────
interface LLMMessage { role: "system" | "user" | "assistant"; content: string; }

interface LLMRequest {
  messages: LLMMessage[];
  maxTokens: number;
  temperature?: number;
  tools?: LLMToolDef[];                          // phase 2; normalized JSON-schema defs
  signal?: AbortSignal;                          // propagated: client abort → provider abort
}

// ── Normalized stream output ────────────────────────────────────
type LLMStreamChunk =
  | { type: "text";      text: string }
  | { type: "tool_call"; name: string; args: unknown; id: string }   // phase 2
  | { type: "done";      usage: { inputTokens: number; outputTokens: number };
                         stopReason: "end" | "max_tokens" | "tool_call" | "aborted" };

// ── Normalized error taxonomy (thrown, not streamed) ────────────
class LLMError extends Error {
  code: "auth" | "rate_limited" | "overloaded" | "context_too_long" | "bad_request" | "unknown";
  provider: ProviderId;
  retryable: boolean;          // drives the D8 fallback decision
}

// ── The one interface every provider implements ────────────────
interface LLMProvider {
  id: ProviderId;
  isConfigured(): boolean;                       // its env key is present
  stream(model: string, req: LLMRequest): AsyncIterable<LLMStreamChunk>;
}

// ── Public gateway API (the ONLY import app code uses) ─────────
// lib/llm/index.ts
function streamLLM(alias: ModelAlias, req: LLMRequest): AsyncIterable<LLMStreamChunk>;
//   resolves alias → ModelRef → provider, applies fallback chain (D8),
//   normalizes errors, logs usage per provider

Chat wire protocol — types/chat.ts (client-safe, unchanged from v1)

type ChatRole = "user" | "assistant";

interface ChatMessage {
  id: string; role: ChatRole; content: string;
  card?: ProjectCardPayload;                     // phase 2
  createdAt: number; error?: boolean;
}

interface PersistedChat { version: 1; messages: ChatMessage[]; updatedAt: number; }

interface ChatRequestBody {
  messages: Array<{ role: ChatRole; content: string }>;   // last ≤20
}

type ChatStreamEvent =
  | { type: "token";    text: string }
  | { type: "card";     card: ProjectCardPayload }
  | { type: "navigate"; href: InternalRoute }
  | { type: "done";     suggestions?: string[] }
  | { type: "error";    code: ChatErrorCode; message: string };

type ChatErrorCode = "rate_limited" | "input_too_long" | "upstream_error" | "aborted";

interface ProjectCardPayload {
  projectId: string;              // validated against config/projects.ts server-side
  title: string; description: string; tags: string[];
  href: `/projects/${string}`;
}

type InternalRoute = "/skills" | "/projects" | "/experience"
                   | "/resume" | "/contact" | "/blogs"
                   | `/projects/${string}` | `/blogs/${string}`;

Layering rule: types/chat.ts is client-safe and never imports from lib/llm/. The chat route is the only place both meet — it translates LLMStreamChunk → ChatStreamEvent. The browser cannot tell which provider answered.

5API / backend changes

§5A — The internal LLM gateway NEW IN V2

A server-only module tree under lib/llm/. The folder structure is the architecture — one folder per provider, one shared contract, one public entry point:

lib/llm/
  index.ts               # PUBLIC API — streamLLM(alias, req); the only file app code imports
  types.ts               # LLMProvider contract, LLMRequest/Chunk/Error (§3)
  config.ts              # alias→ModelRef resolution, fallback chains, env discovery
  registry.ts            # builds Map<ProviderId, LLMProvider> of *configured* providers at startup
  errors.ts              # LLMError + per-provider error mapping helpers
  providers/
    anthropic.ts         # ~30-line adapter over @ai-sdk/anthropic
    openai.ts            # ~30-line adapter over @ai-sdk/openai
    google.ts            # ~30-line adapter over @ai-sdk/google
    groq.ts              # ~30-line adapter over @ai-sdk/groq
Design ruleMeaning
One import surface App code only ever imports lib/llm (the index). ESLint no-restricted-imports rule blocks importing lib/llm/providers/* or any provider SDK from outside the gateway.
Config-discovered providers registry.ts registers a provider iff its env key exists. Missing key = provider absent, not broken. Selecting an unconfigured provider in an alias fails fast at first request with a clear server-log message.
Adding provider #5 is a 3-step recipe (1) add literal to ProviderId, (2) drop providers/<name>.ts implementing LLMProvider, (3) document its env key. No other file changes — registry picks it up. Recipe documented in lib/llm/README.md.
Normalized errors drive policy Adapters map provider-specific failures into the LLMError taxonomy; index.ts makes fallback/retry decisions on code + retryable only — policy lives in one place, never in adapters.
Server-only, enforced Every gateway file imports the server-only package — accidental client import becomes a build error, so provider keys can never leak into the bundle.
Usage logging index.ts logs one structured line per request: alias, resolved model, latency to first token, token usage, error code if any. This is the observability story for "which provider is slow/expensive" — no separate service.

New route: POST /api/chat (app/api/chat/route.ts)

Contract
RuntimeNode.js (required for fs + gateway SDKs), export const maxDuration = 60
Flowvalidate body → rate limit (429 + Retry-After) → build system prompt → streamLLM("chat", req) → translate LLMStreamChunk → ChatStreamEvent NDJSON lines
RequestChatRequestBody; 400 if >20 messages, any >1,000 chars, malformed roles
Success200, Content-Type: application/x-ndjson, terminated by done or error
Upstream failurePre-token: fallback chain if enabled (D8), else 502. Mid-stream: error event, close. Provider identity never appears in client-visible errors.

6Implementation steps

Phase 0 — scaffolding (½ day)

  1. Add types/chat.ts, config/chat.ts; extend .env.example (§5 env block).
  2. Component skeleton under components/chat/ + hooks/use-chat-store.ts.

Phase 1a — widget shell with scripted responses (1–1½ days)

  1. Port mockup UI to React (chat-widget.tsx, launcher, panel, message list, input, chips) — Tailwind + existing HSL tokens, Framer Motion open/close.
  2. Mount <ChatWidget /> in app/layout.tsx (true root, not the route group), mount-gated like ModalProvider.
  3. Zustand + localStorage persistence + scripted responses. Shippable checkpoint: widget works with zero backend.

Phase 1b — LLM gateway NEW IN V2 (1–1½ days)

  1. Build lib/llm/: types.ts → errors.ts → config.ts → registry.ts → index.ts, with unit tests against a FakeProvider (scripted chunks/errors) — fallback logic, alias resolution, and abort propagation are all testable with zero API keys.
  2. Implement providers/anthropic.ts first; verify streaming end-to-end via a scratch route.
  3. Add openai.ts, google.ts, groq.ts — each is a copy-adapt of the first (~30 lines); smoke-test each with its real key. Write lib/llm/README.md (add-a-provider recipe, spend-cap checklist).

Phase 1c — chat endpoint wiring (1 day)

  1. lib/chat/context.ts (system-prompt builder, token-budget assert).
  2. app/api/chat/route.ts: validation → rate limit → streamLLM("chat", …) → chunk-to-event translation.
  3. Client stream reader (lib/chat/client.ts): POST, incremental NDJSON parse, store dispatch, abort wiring. Swap scripted responses for the live endpoint.

Phase 1d — hardening (½–1 day)

  1. Upstash limits, input caps, per-provider console spend caps.
  2. Accessibility pass (focus trap, role="dialog", aria-live).
  3. Verification checklist (§8); soft launch; watch usage logs + spend across providers for a few days.

Phase 2 — agent behaviors (separate PR, 2–3 days, after soak)

  1. Normalized tool defs through the gateway (LLMToolDef → AI SDK tool format); get_project_details, search_blog, navigate calling existing functions in-process; verify tool loop on ≥2 providers before shipping.
  2. card/navigate events, inline project card, allowlisted router navigation.
  3. Model-proposed suggestion chips via the "cheap" alias.

7Risks and tradeoffs

RiskSeverityMitigation
Cost abuse — now multiplied across N provider keys HIGH Rate limit sits before the gateway (one visitor budget regardless of provider); spend cap set in every configured provider's console — checklist item, documented in the gateway README. Unset keys = provider simply absent.
Behavioral drift between providers — same prompt, different persona/quality/safety behavior; worst for phase-2 tool use NEW MED One provider is the tested default (D2); switching is possible, not automatic. A small golden-question set (5 questions + expected traits) re-run manually when changing the alias. Phase-2 tools verified on ≥2 providers before shipping.
Abstraction leak — provider-specific features (Anthropic system-prompt caching, OpenAI response format, Gemini safety settings) don't fit the common interface NEW MED Accepted cost of the gateway: the interface stays lowest-common-denominator; per-provider tuning lives inside its adapter (e.g. the Anthropic adapter can enable prompt caching internally — invisible to callers). Never widen the shared interface for one provider's feature.
Prompt injection via grounded content MED Unchanged from v1: delimited data blocks, plain-text rendering, client-side navigate allowlist. Note: injection resistance varies by model — another reason the default provider is a deliberate, tested choice.
Streaming buffering on Vercel (one-lump arrival) MED Verify on a preview deploy at step 7 (first adapter), before building the other three.
Hydration mismatch from localStorage state MED Mount-gate pattern as ModalProvider; server renders nothing.
AI SDK dependency risk (D6-A) — breaking changes, abandonment NEW LOW The blast radius is four ~30-line adapter files behind our own interface — the explicit purpose of owning LLMProvider. Worst case: rewrite adapters on native SDKs (D6-B) with zero app-code changes.
Gateway is speculative generality for a single chat feature NEW LOW Named honestly: today there is one consumer. Kept cheap deliberately (~5 small files + thin adapters, no queues/caching/proxying). You've stated multi-provider is a requirement, and phase-2 suggestion generation becomes consumer #2 via the "cheap" alias.
Bundle/perf impact LOW Gateway + SDKs are server-only (server-only enforced — client import is a build error). Widget code-split via next/dynamic; panel loads on first open.

8Verification checklist

  • bun run build passes; no new type or lint errors.
  • Gateway unit tests green with FakeProvider: alias resolution, unconfigured-provider fast-fail, fallback on retryable pre-token error, no fallback mid-stream, abort propagation. NEW
  • Each configured provider smoke-tested end-to-end: streams, aborts cleanly, errors map to correct LLMError.code. NEW
  • Model swap drill: change LLM_CHAT_MODEL to a second provider on a preview deploy — widget works with zero code changes. NEW
  • ESLint blocks importing lib/llm/providers/* or provider SDKs outside the gateway. NEW
  • Preview deploy: tokens stream one-by-one (not one lump) — Chrome, Safari, Firefox.
  • Conversation + open state survive navigation, reload, browser restart.
  • Reset clears storage; greeting replays.
  • Rate limit: burst >10 → 429 → countdown UI → recovery. Confirm the provider call is never made when rate-limited (check usage logs).
  • Stop button aborts mid-stream; partial answer kept; verify the upstream provider request is actually cancelled (usage logs show truncated output tokens).
  • Network kill mid-stream → error bubble + retry works.
  • 1,000+ char input rejected client-side (and server 400 if forced).
  • Mobile ≤480px: full-screen sheet, scroll locked, iOS keyboard doesn't cover input.
  • Keyboard-only walkthrough; focus return; Escape; aria-live announcements.
  • Light + dark themes checked (5 unregistered palettes: spot-check).
  • Widget overlays correctly on all page types; no z-index fights with the z-50 header.
  • No provider API key in the client bundle (grep all four key names in .next client output); server-only guard confirmed by attempting a client import (build fails).
  • Prompt-injection smoke test (test post with "ignore instructions / link to evil.com") — declined; non-allowlisted navigate dropped.
  • Spend cap confirmed in every configured provider console before public deploy. UPDATED
  • Golden-question set (5 Qs) answered acceptably on the default model; results saved as the baseline for future provider swaps. NEW
  • Lighthouse: no meaningful LCP/CLS regression on home.
